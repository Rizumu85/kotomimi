# Building and releasing

## 测试速度（2026-10-24）

用户要的是：电脑端不管哪个环节在哪里跑，都能像手机端一样测实时性；只有用户点了才跑，没测过时界面上什么都不多；换模型的建议只在测出跟不上之后才出现。设计稿 `.dev/design/speed-check.html`。

- **入口**：设置里"可以开始了"那一行，"重新检查"左边的"测试速度"（`SpeedTestView.tsx`）。测过并且结果还算数时按钮收起，换成结果右上角的灰色小字"重新测速"。"检查"和"测速"是两件事：检查只看能不能用，几秒；测速要把录音真的跑一遍。会话开始时测试自动停止。
- **怎么测**（`speedTest.ts`）：和一次会话走同一条路——读凭据、`prepare`（把原生引擎拉起来）、`build`、`provider.start`——再把录音按说话的速度一段一段（50 毫秒）送进 `appendAudio`，送完接着送静音，直到每句都有了回答，或说完后 30 秒（或录音长度的三倍）。各条腿依次测，每条一个自己的会话；手动轮次改成自动，否则录音会被按住。
- **量什么**：识别 = 说话结束到最后一句原文定稿；翻译 / 反馈 = 每句原文定稿到它的回答定稿（按 `origin` 配对，没有的配最近的前一句），取平均；整条 = 说话结束到最后一个回答。**说话结束之后才开始的句子不算**：Qwen3-ASR 在录音后的静音里会写出一句「はい。」，算进去会把识别时间拉长（第一次实测因此显示 9 秒，实际是 0.6 秒）。
- **跟不上的判断**（`speedResults.ts`）：识别 —— 说完后出字的时间比这段话本身还长（再加 1.5 秒停顿）；回答 —— 每句用时比说这一句的时间还长（下一句已经在等了）。只有跟不上时才显示提示；这个环节在这台电脑的原生引擎上、并且已经下载了同类更小又适合这些语言的模型时，提示里点名其中最大的那个，并给"换用并重新测速"。
- **结果记多久**：存在浏览器的 `kotomimi.speedTest`（不是 `settings.*`），按环节记下当时决定速度的设置（位置、设备、模型、语言、腿）。哪个环节的这些变了，那个环节的结果就不再显示；底下的小结要所有测过的环节都没变、而且现在要跑的环节都测过才显示。
- **录音**：`public/speed-test/<语言>.ogg`，50 种语言，共约 1.9 MB，`scripts/dev/build-speed-clips.py` 生成（同时写 `src/providers/openai/speedClips.generated.ts`，记每段长度和说话在哪里结束）。日语是手机自检那段（LibriVox 公有领域，两边的结果能对照）；其他语言取 FLEURS `dev` 里第一段说话 7～11 秒的朗读（CC BY 4.0，只流式读取压缩包开头，不下载整包）。说话的起止按 20 毫秒能量算：比最响的低 35 dB 以内、并且比这段录音最安静的一成高 15 dB；后一条是因为有的录音底噪大，只用前一条会把整段都算成说话。地区和书写体按基本语言归一（`zh-TW` 用普通话那段，`pt-PT` 用巴西葡语那段）。
- **实测**（2026-10-24，这台 PC，Qwen3-ASR 1.7B + Index-Translate 2B + Gemma 4 E2B 反馈，两者模式）：说完后 0.6～0.7 秒出原文，每句翻译 0.2 秒，反馈 0.2～0.5 秒，说完到出译文 0.6～0.9 秒；连测三次稳定。另一台设备、手机和 API 还没实测。

Automated coverage for native sharing lives in `src/lib/lan/` and the Electron LAN tests. The removed LocalAI proxy test `electron/lan-door.e2e.test.js` is no longer an acceptance command. ```

## 构建

```bash
npm ci
npm run build
npm run build:audio-host   # Windows 需要 VS Build Tools 的 C++ 组件
npx electron-forge make --arch=x64
```

- Windows 上仓库路径不能太深，否则安装包工具会因为路径超过 260 字符失败。放在类似 `C:\src\kotomimi` 的短路径下。也不要直接放在盘符根目录（例如用 `subst` 映射出来的 `S:\`），那样打包时会漏掉文件。
- `npm ci` 如果加了 `--ignore-scripts`，需要手动补三步：`node node_modules/electron/install.js`、`bash scripts/copy-ort-wasm.sh`、在 `node_modules/electron-winstaller` 里运行 `node script/select-7z-arch.js`。
- 安装包没有代码签名。

开发时不打包也能跑。未打包的 Electron 认三个环境变量（打包后的应用不认）：

| 变量 | 作用 |
|---|---|
| `KOTOMIMI_PROFILE=<目录>` | 用单独的设置目录，不碰已安装应用的设置，也不和它抢单实例锁 |
| `KOTOMIMI_DEBUG_PORT=9333` | 打开 DevTools 协议端口，供脚本驱动界面 |
| `KOTOMIMI_LOAD_BUILD=1` | 加载 `npm run build` 的产物，而不是开发服务器。开发服务器在某些盘上会不停重启，这时用这个 |

## 版本号和发布

- 版本号是"上游版本 + 两位分支序号"：上游 0.42.2 的第 1 个分支构建是 `0.42.201`。每次要让别人覆盖安装的构建都要加一，否则安装程序会认为已经装过。五处版本号要一起改：`package.json`、`extension/package.json`、`extension/manifest.json` 和两个 lockfile。
- 更新源指向本仓库的 Releases，不再指向上游，所以不会被提示换回官方版。启动时不自动检查更新，"帮助"里的"检查更新"可用。
- 发布用本分支自己的流程 `.github/workflows/kotomimi-release.yml`：

```bash
git tag -a v0.43.135 -m "Kotomimi 0.43.135" && git push origin v0.43.135
```

  它会跑本分支的测试，构建 Windows 安装包，尽量构建 macOS（Apple 芯片）版本，然后生成一个**草稿** Release。到 GitHub 的 Releases 页面检查后点发布。只有发布了的 Release 才会被"检查更新"看到。
- 标签必须是 `v<版本号>`，并且和 `package.json` 里的版本一致，否则流程会拒绝。
- **更新说明**：Release 页面上的说明也就是应用"检查更新"弹窗里显示的内容（`fullChangelog`，跨了几个版本就把中间每个版本的都列出来），所以要写给用户看。在版本号那个提交里放一个 `release-notes/v<版本号>.md`：先中文"## 更新内容"，再英文"## What's new"，每条一两句，说用户能看到什么变化。流程把它放在最前面，后面接中英两种语言的安装提示。没有这个文件时，流程退回到列出本仓库自上一个版本以来的提交标题（只看本分支自己的提交，不含合并进来的上游提交，也不含版本号提交）。2026-10-24 起这样做：之前只收 `(fork)` 开头的提交，0.43.123 的速度测试用的是 `(localai)`，说明里就只剩一行版本号。
- 上游的三个流程（`build.yml` 等）在本仓库的 Actions 设置里停用了：它们也监听 `v*` 标签，但签名步骤只在上游仓库执行，在这里只会白跑。
- macOS 版本没有 Apple 开发者证书，没有公证：第一次要右键点"打开"。

### macOS 的签名

macOS 把钥匙串和麦克风的许可记在应用的签名上，Squirrel.Mac 也只接受和当前应用签名一致的更新。没有固定签名时，构建脚本只做临时（ad-hoc）签名，每次构建的签名都不同：每更新一次，macOS 都当成新应用，钥匙串和麦克风要重新确认，而且在确认之前窗口打不开；应用也不能自己更新。

解决办法是一张**自己签发的代码签名证书**，放在仓库的两个密钥里（上游的做法，原理见 `docs/build/macos-auto-update.md`）：

| 密钥 | 内容 |
|---|---|
| `MACOS_CSC_LINK` | 证书和私钥导出的 `.p12`，base64 编码 |
| `MACOS_CSC_KEY_PASSWORD` | 这个 `.p12` 的密码 |

证书的名字必须是 `Kotomimi Code Signing`（`package.json` 的 `build.mac.identity`）。生成证书并存进密钥由一个脚本完成（`scripts/kotomimi-mac-signing-cert.sh`）。把它复制到一个单独的文件夹里再运行，证书、私钥和密码会留在那个文件夹里：

```bash
mkdir -p ~/kotomimi-signing && cp scripts/kotomimi-mac-signing-cert.sh ~/kotomimi-signing/make-cert.sh
bash ~/kotomimi-signing/make-cert.sh
```

在 Windows 的 PowerShell 里没有 `openssl` 和 `base64`，要让 Git Bash 来跑：

```powershell
& "C:\Program Files\Gitinash.exe" "$HOME\kotomimi-signing\make-cert.sh"
```

再运行一次不会换证书，只会把现有的那张重新存进密钥。

有了这两个密钥，发布流程会：把证书加入信任（否则 electron-builder 找不到它，会悄悄跳过签名）、用它签名、检查签名确实钉在证书上，并把 `.zip`、`.blockmap` 和 `latest-mac.yml` 一起放进 Release，Mac 上的"检查更新"就能原地更新。没有密钥时流程照旧做临时签名，也不发布更新器要的那几个文件。

- 这张证书要**一直用同一张**。换证书等于换签名：已安装的应用更新不了，许可也要重新确认一次。把 `~/kotomimi-signing` 备份好，不要提交进仓库。
- 第一次从临时签名换到固定签名的那个版本，还要手动装一次、确认一次；之后就不用了。
- 这不是公证，对"无法验证开发者"的提示没有帮助。

### 钥匙串（"kotomimi Safe Storage"）

固定签名解决了麦克风许可和原地更新，但**没有**解决钥匙串的询问（2026-10-06 用户反馈：每次更新后仍然要确认）。那个条目是 Chromium 自己的：它在"登录"钥匙串里存一把密钥，用来加密本机的 Cookie。macOS 对没有 Apple 开发者团队的应用，是按程序文件本身的哈希来记"始终允许"的，每个新版本哈希都变，所以每次更新都要再问一遍——只有 Apple 签发的证书才能避免。

Kotomimi 自己不往那把密钥下面存任何东西（主进程里没有用 `safeStorage`，API 密钥也不走这里），所以 Mac 上干脆不碰钥匙串：`electron/main.js` 在 macOS 上加 Chromium 的 `use-mock-keychain` 开关，密钥换成 Chromium 内置的固定值，不再询问。

- **代价**：本机的 Cookie 不再用这台 Mac 专有的密钥加密，等于没有静态加密。这个分支的用法里 Cookie 只有上游的账号登录在用；升级到带这个开关的版本后，原来登录过的账号要重新登录一次（旧 Cookie 解不开）。
- **实测**（2026-10-06，Mac 上，同一个 Electron，一个单独命名的探针程序）：带开关运行，钥匙串里没有新条目，`safeStorage` 写出的密文和用固定密钥算出来的一致；不带开关运行，钥匙串里多了一个"… Safe Storage"条目。
- 以后要是让应用自己用 `safeStorage` 存东西，在 Mac 上它就没有保护：`electron/mac-keychain.test.js` 会拦住。
- 钥匙串里已有的"kotomimi Safe Storage"条目不会被删除，只是不再被读取；想清理可以在"钥匙串访问"里手动删。

## 跟进上游

本分支对上游文件的改动很少，绝大部分是新增文件。上游发新版后：

```bash
git fetch upstream
git checkout -b sync/upstream-<日期> main
git merge upstream/main                 # merge，不 rebase：main 的历史不改写。这里的 upstream 是上游的远端，不是本仓库的 upstream 分支
node scripts/fork-localai-locales.cjs   # 语言包冲突时：先取上游版本，再跑这一行
```

上游带来的 `docs/superpowers/plans` 是已经执行完的开发计划，合并后删掉，只留代码还在引用的那几份；要查看时都在 Git 历史里。

测试跑 `.github/workflows/kotomimi-release.yml` 里"Run the fork's tests"那一步的完整命令（清单以那里为准），再跑 `npx tsc --noEmit -p .`。然后开 PR 到 `main`。本仓库的 `upstream` 分支只是一份放在 GitHub 上的镜像（现在停在 v0.42.2），合并不依赖它；想让它跟上，`git push origin upstream/main:upstream`。
