# Kotomimi 手机端

把一台安卓手机借给电脑上的 Kotomimi 做语音识别：声音从电脑传过来，手机识别，文字传回去。

手机上有两个识别引擎，读的是同一个模型（Qwen3-ASR），各用各的文件：

- [audio.cpp](https://github.com/0xShug0/audio.cpp) 0.9.0：电脑版用的那个，模型也是电脑版那批文件。
- [llama.cpp](https://github.com/ggml-org/llama.cpp) b11401：在手机的处理器上读得快一倍左右（量过的两台手机都是）。

借给电脑时用哪个都行，电脑那边看不出区别。自检会把两个都读一遍，说哪个快。

## 给朋友测

1. 装上 `app-debug.apk`（要允许"安装未知来源的应用"）。
2. 下载模型（建议连 Wi-Fi；断了可以接着下）。列表里同一个模型有两行，一行"audio.cpp 用"，一行"llama.cpp 用"（它是两个文件，一个接一个下）。只想借给电脑用，下 llama.cpp 那一行就够了：0.6B 是 0.9 GB，1.7B 是 2.3 GB。要比两个引擎，就把同一个模型的两行都下了：0.6B 两行一共 2.0 GB，1.7B 两行一共约 4.7 GB。在国内不用开代理：模型在 Hugging Face、魔搭（ModelScope）和一个 Hugging Face 的公开镜像上各有一份，开始时各试一小段，哪边快用哪边；分四路同时下，下面会写着进度、速度和来源。中途断了会自己接着下，不用再点。下完会核对。
3. 自检之前：拔掉充电线，关掉省电模式，电量在一半以上；刚下完模型的话先放几分钟，让手机凉下来。
4. 点"自检"，把手机放在桌上别动：别切到别的 App，别锁屏。屏幕上会写着读到第几项、现在在等什么。读完把报告分享回来。
5. 自检说跟得上的话，点"开始共享"，照下面"和电脑连接"试一次真的。

自检要多久：每个模型、每个引擎要读 5 遍（4 线程两遍、6 线程两遍、显卡一遍），每遍之前先等手机凉下来，最少等 10 秒，最多等 3 分钟。所以一个模型两个引擎，凉得快的话四五分钟，一直凉不下来（天热、充着电、带着厚壳）就要半小时；两个模型都下了就翻倍。时间大半花在等上：2026-10-12 在多亲 F22 Pro 上（很慢的手机，插着线）测了两次 0.6B 两个引擎，一次 13 分钟（等了 9 分钟），一次 26 分钟（等了 22 分钟，十遍里六遍等满了 3 分钟）。快的手机上还没测过要多久。

报告里是这台手机自己的数字：芯片、内存、电量和是不是充着电，两个引擎每一遍读一段 14 秒录音用了多久、装入用了多久、占多少内存、读之前和之后的电池温度。不包含任何你自己的声音。

## 怎么看自检结果

倍速 = 一秒钟能读几秒的话。电脑版边听边出字，是把越来越长的同一段话反复读，所以：

- 4 倍以上：跟得上
- 2 到 4 倍：勉强
- 2 倍以下：跟不上

每个模型一块，两个引擎并排，比如 `4 线程：audio.cpp 2.52 / 2.41 倍速   llama.cpp 3.10 / 3.02 倍速`（斜杠两边是先后两遍）。下面一行写着哪个引擎的哪种设置最快、快多少（按两遍的平均算），再下面一行"借给电脑时"是把这个模型借出去会是什么样。报告最后一句"共享用的是"写着现在借出去的是哪个模型、哪个引擎、多快；屏幕上那句"跟得上 / 跟不上"说的也是它。

手机读过一遍会发热，热了就慢。所以每一遍之前，自检都等手机凉下来：电池温度回到开始时的 1°C 以内，或者已经 40 秒不再往下降（凉到头了，每一遍都从这同一个温度开始，一样公平），系统也不再说手机热；两个引擎轮流读（audio.cpp 4 线程、llama.cpp 4 线程、audio.cpp 6 线程、llama.cpp 6 线程，然后同样的再来一遍），谁也不会因为排在后面吃亏。等了 3 分钟还没凉下来就照样读，这一遍在报告里带 `*`。

两个引擎的计时算的是同一段：把录音读进来、听、写出字，不算装入模型。audio.cpp 自己报这个数；llama.cpp 不报，由 App 从它装完模型的那一行开始计到它结束。

2026-10-12 在多亲 F22 Pro（联发科 MT6769，4 GB，插着线）上，Qwen3-ASR 0.6B：audio.cpp 最快 0.58 倍速，llama.cpp 最快 1.05 倍速，都是 6 线程，都跟不上；内存 audio.cpp 占 2.0 GB，llama.cpp 占 1.7 GB；读出的字一样。两个引擎的显卡（Mali-G52）都一用就崩，报告里写的是"显卡：… 用不了"和引擎崩之前说的最后一句。另一台快得多的手机（天玑 9500）上，llama.cpp 读 1.7B 是 2.7 倍速，audio.cpp 是 1.3 倍速。

报告开头的"显卡："是引擎自己报的名字。audio.cpp 平时就报；llama.cpp 平时不报，自检在它用显卡的那一遍多要了一级日志（`-lv 4`），从 `using device Vulkan0 (…)` 那一行里读。只下了 llama.cpp 模型的手机以前在这里写的是"引擎没认出来"。

## 和电脑连接

手机和电脑在同一个 Wi-Fi 下。

**手机上**：点"开始共享"。屏幕上先是"正在装入"，然后是"等电脑连上"和一个地址，比如 `192.168.1.23:8792`。可以锁屏放在一边：通知栏里有一条"正在共享"，在那里也能停。

**电脑上**（Kotomimi 0.43.110 及以后）：设置 → 提供商，最上面「另一台设备」里点"搜索局域网里的设备"。手机会列出来，带手机图标，标着"手机 · 语音识别"。点它一下就连上了：语音识别这一个环节交给手机，翻译和语法反馈不变。

这样连是**边听边出字**，和电脑自己的引擎一样：说话时把到目前为止的这一段反复让手机重读。多久重读一次跟着手机读一次要多久走，所以看到的就是这台手机自己的速度。

搜不到时（比如路由器不让设备互相访问）可以手填：语音识别 → 「API 模型」，API 地址填 `http://<手机上显示的地址>/v1`，模型填 `qwen3-asr-0.6b-q8` 或 `qwen3-asr-1.7b-q8`，"这个 API 需要密钥"关着。0.43.109 及更早的电脑版只能这样手填，而且是一句话说完才出字。

自检里的"倍速"和实际体感的对应（用放慢的电脑引擎模拟的，20 秒日语，前 17 秒是一整段不停的话）：4 倍速时第一句译文比电脑自己的显卡晚约 7 秒，2 倍速晚约 11 秒，1 倍速晚约 29 秒；文字都完整，只是长句子的后半截落后。

**借出去的是哪个**：下载好的每一行都能借。点一下哪一行就借哪一行（会记住），它是哪个引擎用的，共享就起哪个引擎。没点过的话：自检过，就借自检里读得对、又最快的那个；没自检过，就借小的那个模型，同一个模型两行都在时借 llama.cpp 那一行。屏幕上和通知里写着现在是哪个引擎，比如"地址 192.168.1.23:8792 · llama.cpp"。

怎么跑：用自检给这个模型找到的最快的方式，没自检过就用处理器 4 线程。llama.cpp 只在处理器上跑（显卡在试过的手机上不是更慢就是崩）；audio.cpp 自检说显卡最快时会用显卡。

2026-10-12 在 F22 Pro 上，从电脑经过小门读同一段 14.2 秒的录音（每个引擎两遍，中间隔一分钟，都是 6 线程）：audio.cpp 24.4 / 22.7 秒，llama.cpp 14.0 / 13.6 秒（没自检过、用 4 线程时 16.9 / 15.9 秒）。引擎最多占的内存：audio.cpp 2.1 GB，llama.cpp 1.9 GB。两个引擎都是点了共享 5 到 12 秒能用。

**电脑那边看到的不变**：不管哪个引擎在读，手机报出去的模型名都是电脑认识的那两个（`qwen3-asr-0.6b-q8`、`qwen3-asr-1.7b-q8`），请求和回答的样子也一样，所以现在发布的电脑版不用改就能用。电脑说了语言（比如日语）时，两个引擎都照它说的读；没说就让模型自己听。

手机只回答身边的设备：网页发来的请求、用公网域名指过来的请求都会被拒绝（和电脑版共享的做法一样）。现在没有访问密钥，同一个 Wi-Fi 下的设备都能让它识别。

## 自己编

要 Android Studio（带 SDK、NDK 和它的 CMake）；Windows 上还要 Visual Studio 的 C++ 编译器（显卡后端的着色器要用它编一个小工具）。

```bash
# 1. 引擎：从 audio.cpp 的源码编出安卓版，放进 App 里（十几分钟，不进 git）
android/scripts/build-engine.sh

# 2. llama.cpp：编出它的四个版本，放进 App 里（十几分钟，不进 git）
android/scripts/build-llama.sh

# 3. 安装包
cd android && ./gradlew assembleDebug
```

安装包在 `android/app/build/outputs/apk/debug/app-debug.apk`，约 57 MB，其中 llama.cpp 占 36 MB：自检用的 `llama-mtmd-cli` 22 MB（处理器三档各 3.7 MB，显卡那个 10.6 MB），共享用的 `llama-server` 14 MB（处理器三档各 4.7 MB，装到手机上各 10.5 MB；没有显卡版）。不跑第 2 步也能编出安装包，只是没有 llama.cpp：自检报告里会写"这个安装包里没有带"，它的模型也借不出去。

引擎带齐了 ggml 给安卓准备的七档处理器版本（armv8.0 到 armv9.2），运行时自己挑这台手机能用的最快一档，所以同一个安装包在旧手机和新手机上都不吃亏。显卡后端（Vulkan）也编进去了，但只在要用它的那一次才加载：有的手机驱动撑不住它，这样崩掉的只是那一次，处理器照常能用。

llama.cpp 这边是七个各自独立的程序：读一段就退出的 `llama-mtmd-cli`（自检用）有处理器三档（v80、v82、v86）和显卡一个（Vulkan），一直开着等请求的 `llama-server`（共享用）有处理器三档。它们不会在运行时自己挑，所以由 App 看处理器报的指令集来挑：有 dotprod 和 fp16 用 v82，再加上 i8mm 和 bf16 用 v86，否则 v80。挑的那一档要是一跑就报"非法指令"，就退一档再来（自检的报告里会写；共享时自己退，不用管）。它的 `libggml*.so` 和 audio.cpp 的同名却不是同一个版本，放不进同一个文件夹，所以编成不带库的单个程序。

App 给 llama.cpp 的上下文是定死的：自检 1024（`-c 1024`），共享 2048。不定的话它按模型训练时的 65536 留内存，多出两个多 GB：在 4 GB 的手机上，系统为了腾地方把后台的 App 连同这个 App 一起关掉了（2026-10-12）。共享的 2048 是这么来的：声音一秒占 13 个词元，外加二三十个；写出来的字一秒 3 到 5 个。一分钟的话连声音带字 1000 出头，放得下还有富余；最长收 90 秒，再长就回"太长"。代价是内存：每 1024 个词元 112 MB，两个大小的模型一样。在 F22 Pro 上量的（0.6B，读完一段之后引擎自己占的 / 最高到过）：1024 是 1.18 / 1.76 GB，2048 是 1.30 / 1.91 GB，4096 是 1.53 / 2.13 GB，读得一样快。

共享时 llama.cpp 的引擎只听手机本机，还要一把每次现编的钥匙才回答，钥匙只有这层小门有：不然手机上别的 App、手机浏览器里开着的网页都能让它读。它读过的东西不留（`--cache-ram 0`）：不关的话它会把读过的每一段都存着，最多存到 8 GB，在电脑上试的时候涨到了 9 GB。

从电脑上直接让手机做事：

```bash
adb shell am start -n io.github.rizumu85.kotomimi.node/.MainActivity --ez selfcheck true
adb shell cat /sdcard/Android/data/io.github.rizumu85.kotomimi.node/files/report.txt
adb shell am start -n io.github.rizumu85.kotomimi.node/.MainActivity --ez share true
curl http://<手机地址>:8792/v1/models
adb shell am start -n io.github.rizumu85.kotomimi.node/.MainActivity --ez share false   # 停止共享

# 这一次借出指定的那一行（App 里自己的名字，llama.cpp 的带 llama- 前缀），不改记住的选择
adb shell am start -n io.github.rizumu85.kotomimi.node/.MainActivity --ez share true --es model llama-qwen3-asr-0.6b-q8
adb shell am start -n io.github.rizumu85.kotomimi.node/.MainActivity --ez share true --es model qwen3-asr-0.6b-q8

# 自检或共享时先用 llama.cpp 的某一档（v86、v82、v80），而不是它自己挑的：看退档那条路用的
adb shell am start -n io.github.rizumu85.kotomimi.node/.MainActivity --ez selfcheck true --es llama v86
adb shell am start -n io.github.rizumu85.kotomimi.node/.MainActivity --ez share true --es llama v86
```

## 手机对外提供什么

端口 8792（故意不用电脑版共享的 8790：现在发布的电脑版会搜 8790，搜到手机就会把它当成一台有整条管线的设备列出来，选了却连不上）：

- `GET /v1/models`：借出去的那个模型，用电脑认识的名字（`qwen3-asr-0.6b-q8` 或 `qwen3-asr-1.7b-q8`），不管是哪个引擎在读。回答里带 `X-Kotomimi-Name`（手机的名字）和 `X-Kotomimi-Node: engine`（这里是识别引擎本身，不是一台电脑的整条管线）。
- `POST /v1/audio/transcriptions`：一段声音整段读一遍（OpenAI 的格式：`file`、`model`、`language`），回答 `{"text": "…"}`。

引擎自己只听手机本机（127.0.0.1:8793），外面的请求都经过这层小门。

借出去的是 audio.cpp 时，请求原样转给它，这本来就是它自己的接口。借出去的是 llama.cpp 时，小门替它翻译：llama.cpp 的服务没有这个接口，只能当成一次对话来问（`/v1/chat/completions`，声音作为对话里的一段音频），模型回的是 `language Japanese<asr_text>……`，小门只把 `<asr_text>` 后面的字放进 `{"text": …}` 里回给电脑。其余的：

- **语言**：电脑说了语言（`ja`、`zh`、`en` 这样的代码，或者英文名），小门就替模型把回答的开头写好（`language Japanese<asr_text>`），模型接着往下写。这是这个模型被告知语言的办法，audio.cpp 在里面也是这么做的。短的时候差别大：电脑是从第一秒就开始读的，而让模型自己听的话，1 秒的日语对话三次里有一次被当成别的语言（写成中文、粤语或英文），2 秒六次里一次，4 秒二十多次里一次，15 秒没错过（2026-10-12，8 分钟真实对话，在电脑上用同一个版本量的）；15 秒的那 32 段，说不说语言写出来的字一模一样。电脑说的是模型不认识的语言，就不说，让它自己听。
- **写多长**：模型偶尔会迷路，一直重复同一个词直到被掐断，电脑那边自己会把这种回答剪掉。小门按声音的长度定一个上限（96 + 每秒 12 个词元），够电脑认出来是在重复，又不至于没完没了。正常的话一秒只写 3 到 5 个。
- **一次读一段**：同时来两段，后一段等前一段读完。等的那台电脑不等了（断开了），就不读它那一段。
- **不对的请求**：不是表单、表单里没有文件、文件不是 WAV，回 400；太长回 413（llama.cpp 借出时 90 秒，audio.cpp 借出时 30 秒：audio.cpp 占的内存跟着声音的长度涨，2026-10-12 一分钟的静音在 4 GB 的手机上涨到系统把 App 杀掉；电脑边听边出字一次最多送 15 秒左右）。这些检查两个引擎都做：以前 audio.cpp 借出时请求是原样转给引擎的，一个不是表单的请求能让引擎去打开手机上指定的文件；引擎没回答、回答看不懂，回 502。都带一句英文说明。空的 WAV 直接回空字。

`model` 那一栏小门不看：手机借出去的只有一个模型。

## 还没有的

- 内存不够时先说出来：4 GB 的手机读十几秒的长段时会被系统因内存不足杀掉（2026-10-10 在 F22 Pro 上）。
- 访问密钥。
- 小样里的样子（`.dev/phone-node/`，杏橙薄荷那一版）：现在只用了它的颜色。
- Nemotron 和 R2T2：引擎里已经编进去了，App 里还没列出来。

自检用的录音有两段：

- 英文：LibriSpeech 里的一段朗读（14.2 秒，CC BY 4.0），随 audio.cpp 的源码一起来，`build-engine.sh` 把它放进安装包。速度都是用它量的。
- 日语：LibriVox 朗读的芥川龙之介《杜子春》第一段里的一句（8.6 秒；LibriVox 的录音是公有领域的，[toshisyun_um_librivox](https://archive.org/details/toshisyun_um_librivox) 的第 1 个文件，29.75 秒起），在仓库里：`app/src/main/assets/selfcheck-ja.wav`。每个引擎读一遍，看读得对不对：这个应用是拿来听日语的，一个引擎的某一档在这台手机上把英文读对了，不等于把日语也读对了。

**读得对不对**：每一遍读出的字都和这段录音说的比（只比字母和数字，标点、空格、大小写不算），错的超过二十分之一就算读错，读错的那一遍不算成绩。"这段录音说的"是两个引擎、两个大小的模型在电脑显卡上写出来的字：英文那段四种写法只差两个逗号；日语那段选的是四种写法都一样的一句（开头几句里的"洛陽""杜子春"各写各的，当不了标准答案）。2026-10-12 在 F22 Pro 上：英文两个引擎都一字不差；日语 audio.cpp 的 0.6B 把"使い尽くして"写成"使いつくして"，错 1 个字，在电脑上它也这样写。

哪个引擎更准，不用手机量：同一个引擎、同一个模型、同一段声音，在哪台设备上写出来的字都一样。2026-10-12 在电脑上用八段真实的日语对话比过（每段一分钟，切成 15 秒读），两个引擎差不到一个百分点（1.7B：audio.cpp 28.2%，llama.cpp 27.6%，和一个更大的模型的识别结果比）。
